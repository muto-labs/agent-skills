# Maintain, version and export
Version 0.3.0 | 2026-10-11
## Current knowledge and history
Maintain one current KB; preserve historical source/synthesis snapshots separately. Current fields override older dated notes. Remove answered questions from current next-actions. Never lose raw stories or original writing when condensing.
Keep current accepted assets and prior versions in an [asset index](asset-index.md). Index states: draft, reviewed/accepted for reuse, public-use approved for specified version/context, published, verified, superseded. Mark impacted assets stale when material KB changes, without automatic rewriting/publication.
## Naming
Every leader output includes chosen name/initials and version: <initials>-<asset>-v0.1.md. Generic standard templates remain generic. Rename references/registry together. Keep originals, source dates and context; exact file names can vary by platform.
## Change procedure
Explicit facts/corrections: record source/date. New inferred identity/voice: propose for review. Small accepted corrections do not require re-review of every unchanged paragraph.
Standard improvements: separate universal method changes from personal preference; version both standard and copied reference set, preserve overrides, validate links and state. Do not duplicate evolving method instructions across uncontrolled files.
## Privacy
Maintain private source KB and public-safe briefs as distinct artifacts. Public-draft eligibility is not approval to publish. Exclude restricted information from exports; other people's data is not covered by leader openness.
## Review and metrics
At requested intervals or material changes: assess objectives, knowledge, accepted edits, promises, effort and outdated assets. Schedule only if requested. Link updates to affected assets. Include enough detail to resume after interruptions without restarting.
## Portable delivery
Entrypoint, selected references, relevant KB and assets form a file package. Scripts are optional and plain Markdown fallback must work. Test actual target-tool behavior before claiming compatibility; native installation and authentication are separate. File validation alone is not behavioral validation.

## Dashboard lifecycle
Create the same minimal dashboard during package initialization, before interviewing. Rebuild after meaningful saved knowledge, progress, time, asset or review changes before ending the turn. See dashboard-guide.md; preserve the stable HTML path and do not infer completed work from dashboard creation.

## Everyday application
Use the reflection recorder, asset freshness map and agent briefing practices in [the Fuel catalog](activities.md#everyday-practices). They are ongoing habits, not separate onboarding requirements.
